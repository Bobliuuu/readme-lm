## X5 numbers (M-series Mac, 10 cores, single-threaded transform)
- Tokens processed: 22 prompt + 114 generated chars = 136 steps (KV-cached).
- xsltproc: 197 s wall (147 s user CPU, partly contended by a concurrent Chrome run) => about 1.1 to 1.4 s per token. Peak RSS 208 MB. Default xsltproc recursion limit was enough (no --maxdepth).
- Chrome 156.0.8078.80 headless on a localhost http server: 163 s wall, same exact answer. Page is blocked (single main thread) the whole time. Chrome 156 also injects an `xslt-warning-banner` deprecation banner.
- Data: model.xml 10.7 MB (1.5 MB gzipped), qa.xsl 11.6 KB, lib.xsl 24.6 KB (generated, weight-free). Weights stay pure DATA; the code is generic.
- Throughput about 0.5 M multiply-adds/s. Naive version (data-indexed `$x[$i]`, RTF of products) was 0.19 M MAC/s.

## Engineering findings (what makes it work/fast)
- XSLT 1.0 has no exp, no vector ops, no elementwise product of two node-sets. Dot product = one long unrolled XPath expression `$w1[1]*$x1[1]+...` inside a named template; sum/product in XPath doubles are exact enough (matches numpy to 1e-7 on logits).
- XPath positional `$v[j]` on a node-set is O(j) in libxslt. Rows are therefore stored as `<c>` chunks of 32 `<v>`; chunk size 8: 13.8 s, 16: 8.7 s, 32: 6.9 s, 64: 8.7 s for the same 8-token benchmark (flat 128/512: 22 s).
- Own exp (range reduction /128, degree-12 Taylor, 7 squarings), own sqrt (scale by 4, 8 Newton steps), erf by Abramowitz-Stegun. RoPE cos/sin come from a data table (256 positions) since XSLT 1.0 has no trig.
- Needs `exsl:node-set` (to read result-tree fragments). Autoregression = tail-ish recursion; each step returns only new KV `<kr>` rows; cache grows by node-set union (no copying).
- Chrome vs EXSLT, tested in Chrome 156: system-property vendor = libxslt, version 1.0; `exsl:node-set` AVAILABLE; `math:exp` (EXSLT math) NOT available (xsltproc has it). So the exp series was necessary, not optional. Safari uses the same libxslt (not tested here, no Safari run).

## Input story (no JS)
XSLT 1.0 in browsers cannot read the URL query/hash, cookies or a form. Options:
1. Prompt inside the XML: `<ask><q>what is qwentpu</q></ask>` with `<?xml-stylesheet type="text/xsl" href="qa.xsl"?>` (this is what web/qwentpu.xml does; also supports `max`, `forced`).
2. One page per question: only pre-authored questions, each costs the viewer about 3 minutes of frozen tab. Arbitrary viewer prompts are impossible without a server or JS.
3. A viewer can fork/edit the XML on GitHub and let Pages rebuild: not interactive.
So interactive Q&A is NOT achievable; only "pick one of N prepared pages".

## Hosting story
- The GitHub README is Markdown rendered through a sanitizer: no xml-stylesheet, no XSLT. The transform cannot live in the README itself.
- GitHub Pages serves static .xml, so `page.xml` with the xml-stylesheet PI would run in the viewer's browser (same-origin xsl, xsl:import, document('model.xml') all worked on localhost http; file:// not tested). I did NOT publish anything, so the Pages MIME types (xml, xsl) are unverified here. The README could only link to such a page.
- A 10.7 MB model.xml is fine for Pages (1.5 MB over the wire if gzip is applied), but the browser must parse it (about 100 MB of DOM).

## Browser support status (as of 2026-11-08)
- Chrome: officially deprecated in Chrome 143 (2025-12-02); enterprise policy Chrome 146; origin trial Chrome 152 (2026-08-25); WebView early disable 154; **XSLT stops working on Stable in Chrome 158 on 2026-11-17** except for origin-trial/enterprise-policy users; both are shut off in Chrome 176 (2027-08-17). Both XSLTProcessor and the `<?xml-stylesheet type="text/xsl"?>` PI are removed (the PI remains for CSS). Sources: https://developer.chrome.com/docs/web-platform/deprecating-xslt (some copies of the timeline say M155/M148 for individual steps; the developer page says 158 for stable removal). Local Chrome 156 still runs XSLT but shows a red warning banner.
- Firefox: Mozilla tracking bug https://bugzilla.mozilla.org/show_bug.cgi?id=1990759 (NEW; console warning, enterprise policy resolved; "disable by default in Nightly" assigned). A secondary source (https://dev.to/alanwest/chrome-158-removes-xslt-on-nov-17-heres-what-breaks-and-how-to-fix-it-206c, ISO notice https://committee.iso.org/sites/tc81/home/news/content-left-area/news-and-updates/news-12.html) reports an Intent to Unship (2026-08-26) with disabling in all channels in August 2027. I could not confirm that from a Mozilla primary source.
- Safari/WebKit: WebKit's standards position is "positive" on removal, no dated plan found (https://lwn.net/Articles/1034560, Chromium intent thread https://groups.google.com/a/chromium.org/g/blink-dev/c/CxL4gYZeSJA). Firefox for iOS uses WebKit.
- Chrome rationale: remove libxslt (vulnerable); usage about 0.02% of page loads.
- Net: from 2026-11-17 the demo stops working in default Chrome/Edge; it would only work through an origin trial token (per-origin, until 2027-08-17) or in Safari/Firefox for some more months.

## Scaling to GPT-2 124M (extrapolation, not measured)
- MACs per token: ours about 0.6 M weights + attention; GPT-2 about 124 M (85 M blocks + 38.6 M tied 50257x768 head) = about 200x. At 0.5 M MAC/s that is about 4 minutes per token, ~80 min for a 20-token reply (xsltproc, the engine family of Chrome).
- Data: 124 M `<v>` nodes: about 1.3 GB of XML text at ~10 B/weight; libxml2 tree about 60 to 100 B/node, so 8 to 12 GB RAM for the DOM. libxml2 and browsers have parser limits (huge-document guards); a browser tab would die. Quantized/packed text (e.g. 4-bit hex strings) would need substring/translate decoding in XSLT, costing more time.
- Conclusion: 600K model is the ceiling for this substrate in practice (about 0.5 to 1 minute per 20 tokens); GPT-2 is infeasible.

## Blockers
1. Chrome Stable removal on 2026-11-17 (hard, dated). Origin trial only for opted-in origins, ends Aug 2027.
2. No interactive input without JS; only prompt-in-XML / one page per question.
3. Speed: ~1.1 s/token, whole tab frozen for ~3 min on the demo answer; no progressive output (text appears when the transform finishes).
4. Not embeddable in the README (Markdown sanitizer); needs a separate Pages URL.
5. Relies on `exsl:node-set` (works in Chrome libxslt; not in pure XSLT 1.0 spec). `math:exp` is absent in Chrome, hence the series.
6. Unverified here: Safari run, Firefox (TransforMiiX) run, GitHub Pages MIME types, Chrome memory.

`python3 export_model.py` (CH=32), `CH=32 python3 gen_lib.py`, then `xsltproc qa.xsl ask_qwentpu.xml`. Both scripts default to CH=32 (best chunk size). Test drivers: x1.py, x2.py, x3.py, x4.py.
